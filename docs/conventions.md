# 규약 (conventions)

FE/BE 2분할 DDD 프레임워크의 공통 규약. 스킬·에이전트가 이 문서를 공유 기준으로 삼는다.

## 분할 축 (핵심)
- **최상위 분할 = FE vs BE.** 한 도메인이 둘을 다 짊어지지 않는다(수직 도메인 금지 — 기능이 쌓이면 비대해진다).
- **FE 도메인** = 플로우(오케스트레이션) + 표현(V)만. 기능 구현 로직 금지.
- **BE 도메인** = 데이터(M) + 기능(C)만. 플로우 순서·화면·연출 금지.
- **참조는 단방향: FE → BE.** FE 요소가 BE 기능을 **링크로만** 부른다. BE는 FE를 모른다. BE 도메인 간 의존도 단방향·비순환.
- **참조 그래프 = HOME 단일 소스.** `docs/HOME.md`의 `## 참조 그래프`가 도메인 의존의 단일 출처다 — 에이전트는 이걸 읽고 영향 범위를 파악할 뿐, 도메인 폴더를 탐사해 그래프를 재구성하지 않는다. 따라서 **FE→BE 호출이나 BE→BE 의존을 추가/삭제하면**(요소 링크·README `depends` 변경) **같은 변경에서 HOME `## 참조 그래프` 엣지도 갱신한다.** 새 도메인 경계가 생기면 decompose가 다시 그리고, 기존 도메인의 엣지만 바뀌면 그 변경을 한 주체(plan/intake)가 갱신한다 — 둘이 어긋나지 않게.
- 기능 추가 = 폴더에 **파일 추가**(FE는 `요소/<노드>.md`, BE는 `기능_<name>.md`)이지 한 문서를 부풀리는 게 아니다.
- **순서는 두 방향이다.** ① **기획 순서 = sketch 기반 FE/BE 코스펙** — sketch 목업이 FE 플로우·화면 데이터를 구체화해 두면 decompose가 FE·BE 경계를 firm하게 긋고(잠정 아님), plan-fe·plan-be를 **sketch를 공유 단일 소스로 짝지어 한 패스에서** 깐다(FE=호출자 플로우/요소, BE=그 호출이 닿는 데이터/기능). sketch가 없으면 **FE-first 폴백** — plan-fe로 FE를 먼저 구체화하고 그 호출에서 BE를 도출한다(이땐 decompose의 BE가 잠정). 어느 경로든 **참조는 FE→BE 단방향이고 BE는 '언제 부르나'를 모른다**(코스펙은 동시에 깔 뿐 이 불변식을 깨지 않는다). ② **구현 순서 = BE-first** — FE가 부르는 기능이 먼저 있어야 하므로 dev/ticket이 HOME 참조 그래프로 BE→FE 위상 정렬. 둘을 혼동하지 않는다.

## 분할 granularity (위키-정렬 세분할)
도메인 경계 = **LLM Wiki 구조 자체**다. 기능/관심사별로 잘게 가른다 — 기획→개발이 위키 골격을 1:1로 따라가도록(`docs/HOME.md`가 곧 위키 해부도). **boundary-YAGNI로 굵게 합치지 않는다**: 의심스러우면 합치는 게 아니라 가른다.
- **분할 기준은 "책임이 다른가"가 아니라 "각자 자기 데이터/관심사를 소유하는가".** 얇아도 별개 관심사(예: HITL 검토)면 분리가 정당하다. 단 공유 필드는 **소유자 1개 + 단방향 참조**(BE 데이터 단일 소유 규칙과 일관).
- 게이트에서 **반사적 merge(하나로) 추천을 하지 않는다.** 합치는 건 두 관심사가 실제로 같은 데이터를 한 주체로 소유할 때만, 사람이 명시 결정.

## 위키 루트
- 위키 루트는 `docs/` 직접.
  - `docs/HOME.md` — 도메인 지도(FE/BE 목록 + FE→BE 참조 그래프).
  - `docs/CONTEXT.md` — 용어·공유 개념.
  - `docs/fe/<name>/` — FE 도메인 폴더.
  - `docs/be/<name>/` — BE 도메인 폴더.
  - `docs/arch/ARCHITECTURE.md` — 전역 규약 + 기술 스택(arch 산출).
  - `docs/brainstorming/` — brainstorm 설계 브리프.
  - `docs/roadmap.md` — 버전 로드맵(v1→vN 스코프 표 + **현재 타깃 버전**, roadmap 산출).

## 버전 게이트 (현재 타깃 버전)
- `roadmap`이 핵심 기능 목록을 버전(v1→vN, 가변 N)으로 자르고 `docs/roadmap.md`에 **현재 타깃 버전**을 표시한다(MVP=v1). 버전 경계·우선순위는 AI가 짓지 않고 사람이 확정한다.
- `decompose`·`plan-fe`·`plan-be`·`ticket`은 **현재 타깃 버전의 포함 기능** 범위 안에서만 돈다 — 범위 밖 기능은 다음 버전 슬롯에 둔 채 도메인으로 가르거나 명세하지 않는다. roadmap이 없으면(버전 미적용 프로젝트) 기능 전체가 범위.
- 버전을 올리려면(현재 버전 출시 후 다음 착수) `docs/roadmap.md`의 현재 타깃 버전 줄을 사람이 갱신한 뒤 decompose부터 다시 돈다.

## FE 도메인 (`docs/fe/<name>/`)
- 표준 구조: `README.md`(도메인폴더-README 템플릿) + `플로우.md`(루트 고정·단일, mermaid + FE 전체 값) + `요소/<노드>.md`(노드 1 = 파일 1, 요소 템플릿) + `일지.md`.
- 요소 §호출하는 기능 = BE 도메인 기능 **링크만**. 구현 로직 금지.
- 금지: 플로우를 단계폴더(C/·M/·V/)에 두기, 노드 상세를 `요소/` 밖에 흩뿌리기.

## BE 도메인 (`docs/be/<name>/`)
- 표준 구조(평평): `README.md` + `데이터.md`(M, 소유 테이블/enum 한 파일) + `기능_<name>.md`(C, 기능당 1파일) + `일지.md`.
- 공유 데이터는 `데이터.md`에 한 번만, 기능은 링크 참조. 기능 문서는 "무슨 데이터를 읽고 어떻게 처리하나"만(언제 부르나는 FE가 정함).

## 연동 방식 (sync/event) — 참조 그래프 엣지 표기
HOME `## 참조 그래프`의 각 엣지는 **동기 호출(sync, 기본)** 또는 **이벤트 구독(event)** 이다. 엣지 끝에 `[event]`로 표기하고 없으면 sync.
- **엣지 방향 = "A가 B에 의존"**. sync면 A가 B의 함수를 직접 호출(`A → B`, A가 B를 앎). event면 **구독자가 발행자의 이벤트 계약에 의존** — 등급이 결제 이벤트를 구독하면 `be/grade → be/payment [event]`이고 **결제는 등급을 모른다**(역방향 엣지 없음). 런타임 오케스트레이션 선택이 엣지 방향을 정한다.
- **event 엣지의 T1 계약면**은 함수 인터페이스가 아니라 **발행되는 이벤트 페이로드 스키마**다.
- 표기 예:
  - `- fe/checkout → be/payment`           (sync 기본)
  - `- be/grade → be/payment  [event]`      (grade가 payment 이벤트 구독)
- home-check·context-pack은 `[…]` 태그를 슬러그에서 떼어내 엣지 정합성을 비교한다(태그는 엣지 식별자가 아니라 메타데이터).

## 인터페이스(계약면) — 컨텍스트 팩 슬라이싱
도메인을 repomap식 컨텍스트 팩으로 압축 주입하기 위한 규약. 각 도메인 문서는 **계약면(caller가 알아야 할 면)** 과 **본문(그 도메인 구현자만 보는 면)** 으로 갈린다. 팩 생성기가 이웃 도메인을 **T1(인터페이스 스켈레톤)** 으로 줄일 때 계약면 섹션만 남기고 본문을 버린다. **표준 섹션 제목 = 슬라이싱 키이므로 표준 섹션을 리네이밍하지 않는다.**
- **기능_*.md (BE C)** — 계약면: 제목 + 한 줄 요약 · `## 입력` · `## 출력·변경`. 본문: `## 다루는 데이터`(링크) · `## 처리` · `## 예외·경계`.
- **데이터.md (BE M)** — 계약면: 각 테이블 이름 + 필드·타입(스키마 shape) · enum **값 이름**. 본문: 의미·값·범위 칸 · enum 의미.
- **README(도메인폴더)** — 전부 계약면(작다). frontmatter `kind`/`pattern`/`depends` + 한 줄 + `## 구성` + `## 책임지지 않는 것`이 이웃 도메인 요약의 1차 소스.
- **요소.md (FE V)** — 계약면: `## 호출하는 기능`(FE→BE 엣지 선언 = HOME 정합성 체크 근거) · `## 내보내는 값 (출력)`. 본문: 진입·트리거 · 로드값 · 분기·전이 · 화면·연출. (FE는 호출당하지 않아 T1로 잘 안 뜨지만 정의는 둔다.)
- **플로우.md (FE)** — 계약면: mermaid 그래프 + `## FE 전체 값`. 본문: 전역 연출.
- **티어**: **T0**(타깃 도메인) 전문 · **T1**(1홉 직접 의존) 계약면만 · **T2+**(전이 의존) HOME `## 도메인` 표의 한 줄 역할만. `일지.md`는 **전 티어 제외**(write-only).
- 팩은 **HOME `## 참조 그래프`를 진실로 신뢰**한다 — 요소 `## 호출하는 기능` 링크·README `depends`가 HOME 엣지와 어긋나면 팩이 거짓이 된다. 엣지 변경 시 HOME 동기화(§분할 축)가 이 팩의 안전장치다. `node scripts/home-check.mjs --root <docs>`가 이 정합성(역산 엣지 ↔ HOME, 미등재 도메인, 순환)을 검증한다(exit 1=불일치). **CI(.github/workflows/ddd-check.yml)가 이를 게이트로 돌린다(탐지만).** 불일치로 막히면 손으로 HOME을 고치지 말고 `graph-sync` 스킬(= `home-check --fix`)로 **선언에서 HOME을 재조정**한다 — 빠진 엣지 추가·stale 제거, `[event]`·주석 보존, 새 엣지는 연동방식 확인 후 사람이 커밋.

## 코드 골격(Tier B) — 위키는 계약에서 멈추고 그 아래는 추론에 위임
위 §인터페이스가 **도메인 간(선언된 위키 계약)** 을 다룬다면, 코드 골격은 **도메인 안(파생된 코드 구조)** 을 다룬다. 둘은 정반대로 관리한다.
- **md에 코드 구조를 절대 적지 않는다.** 위키는 *계약*(입력/출력/데이터 shape)에서 멈춘다. 그 아래 클래스·함수 구조는 **코드에서 tree-sitter/ctags로 파싱해 시그니처 골격**(본문은 `⋮…`로 접음)으로 추출한다 — 손으로 나열·유지하지 않는다(클래스 수백 개를 md로 관리하는 건 불가).
- **골격은 파생 캐시다.** `.ddd-cache/`(gitignore)에 `경로+mtime` 키로 두고 **쓸 때(디스패치) 재생성**, 바뀐 파일만 증분 파싱. 코드가 진실이라 드리프트 불가 — 검증 불필요(반대로 HOME 계약은 저작된 진실이라 home-check로 검증).
- **골격 = 순수 시그니처만.** docstring은 안 긁는다(stale 위험). "무엇이 있나"(이름·시그니처)는 골격이, "어떻게 동작하나"는 작은 도메인이라 본문을 온디맨드로 읽어 해결(읽은 본문은 ground truth). 의도는 위키 계약이 담당.
- **코드 위치 = `code:`(README frontmatter).** 기본 `src/<slug>`로 계산되며(예 `be/payment` → `src/be/payment/`), 레이아웃이 다를 때만 한 줄 명시. **dev가 규약으로 유지**하고(코드를 규칙대로 두거나 `code:` 명시), `home-check`가 **백스톱**으로 그 경로 존재·비어있지 않음을 검증(향후 import↔depends 대조까지 확장 — slug↔코드 매핑이 그 다리).
- LLM에 넘기는 한 장 = **①타깃 계약(위키 T0) + ②이웃 인터페이스(T1) + ③타깃 코드 골격(Tier B, 기존 코드 있을 때만)**. ③은 거리로 안 자르고 타깃 도메인 하나만 통째(경계로 작아서) — 재작성 방지용 up-front 인식.

## 값 생성 금지
- AI는 수치·수량·비율·규칙·계산식·enum 값 의미를 **짓지 않는다**.
- 빠진 값은 `*[입력 필요: …]*` 슬롯으로 비운다. AI가 짓는 건 ① 뼈대 문장 ② 슬롯 ③ 질문.
- 빈 슬롯이 남은 도메인은 dev 오케스트레이션/implement.ps1에서 막고(기획 트랙=plan으로) 사람에게 돌린다.

## 일지 하네스 (쓰기 전용)
- `일지.md`는 **쓰기만 하고 읽지 않는다** — 디버깅용 결정 로그다. 쌓인 이력을 매번 읽으면 토큰만 늘고 환각을 부른다(필요할 때 사람이 본다).
- 의미 있는 변경(데이터 구조·규칙·스키마·enum·관계·플로우·시점 등 "이렇게 하기로 했다") 후 `일지.md`에 항목 1개 추가 + `현재 상태 요약` 갱신.
- 오타·링크 정리 같은 무가치 변경은 제외.

## 패턴 정책 (TS/DM)
- **BE 도메인**에만 적용(기능 C의 로직 패턴). FE는 플로우+V라 해당 없음.
- 도메인별 기본값을 `docs/arch/ARCHITECTURE.md` §패턴 정책에서 정한다 — **기획(코스펙·distill) 후 `arch` 단계**에서 기술 스택과 함께 결정.
  - **TS(트랜잭션 스크립트)** — 단순 CRUD·절차적, 규칙이 얇을 때.
  - **DM(도메인 모델)** — 규칙·불변식·상태가 풍부할 때.
- BE 도메인 `README.md`에 채택값 + 근거. 기본값과 어긋나면 갈림길로 올려 묻는다.

## 명명·언어
- 코드·식별자: 영문. 주석·문서: 한국어. 도메인 slug 영문(`fe/`/`be/` 트랙), 요소·기능 파일명 한국어 허용.
- 명명·직렬화 컨벤션은 ARCHITECTURE를 따른다.

## 구현 경계
- 구현 에이전트(`dev`)는 **개발 리드**다 — 개발 사항을 받으면 티켓으로 분해해 **티켓 서브에이전트**로 발행하고, 사람 승인 후 worktree에서 **구현 서브에이전트**로 구현시킨다(intake/직접 호출 경로). 단일 도메인·티켓을 배정받으면 **리프**로 그것만 계약서대로 구현한다(서브에이전트로 불릴 때). 도메인 여럿/지도 전체 구현도 별도 빌드 진입점 없이 dev가 HOME 참조 그래프로 BE→FE 정렬해 디스패치한다. 계약이 FE/BE를 선언하므로 트랙별 에이전트를 가르지 않는다(구현 에이전트는 한 종류).
- 경계 밖 파일 수정·재설계·리네이밍·겸사겸사 리팩터·새 의존 추가 금지. 참조 도메인(FE→BE, BE→BE)은 읽기만.
- 모호하거나 빈 슬롯이면 멈추고 보고. push는 사람이.

## 변경 접수 (raw → intake)
- 운영 중 들어오는 회의록·신규 기획·리팩토링 문서는 `raw/*.md` 인박스에 떨군다. `intake` 스킬이 스캔하고, 문서 1개당 git 브랜치(worktree)에서 `intake` 에이전트를 1개씩 돌린다.
- `intake` 에이전트(종합 창구)는 문서를 **부분별로** 가른다: **새 도메인 경계** 필요 → 멈추고 사람에게 `decompose` 반환(경계는 사람 게이트, AI가 경계를 짓지 않는다). **기획 부분** → `plan`이 문서 수정(+비전·FE 플로우가 크게 바뀌면 `sketch`로 목업 갱신); 개발이 유발되면 plan이 "개발 인계 메모"를 올려 dev로 넘긴다. **개발 부분** → `dev`가 티켓으로 분해·발행하고 멈춤(사람이 티켓 검수) → 재트리거 시 `dev`가 구현(2단계 정지). 한 문서가 기획·개발을 둘 다 담으면 plan 먼저 → dev. 계약·경계를 넘는 일을 발견하면 dev는 짓지 말고 intake로 역류시킨다.
- 모든 intake 작업은 배정 브랜치에 **로컬 커밋만** — push·merge·PR은 사람. 처리된 문서는 `raw/_done/`로 옮겨 중복 접수를 막는다.

## 단계별 에이전트 분담
- 기획 전단 단계는 메인 스레드 스킬로 직접 부르거나 서브에이전트로 돌릴 수 있다. brainstorm(아이디어 다듬기)·sketch(비전 목업 합맞춤)·roadmap(버전 스코프 자르기)은 사람과 대화로 확정하는 단계로 남고(brainstorm은 거시 목표 구체화 전에 리서치 서브에이전트 3트랙을 병렬로 돌리고, sketch는 합맞춤용 저코스트 목업 HTML을 콜드 서브에이전트로 생성한다), 나머지는 전부 에이전트 처리된다.
- `research` — brainstorm 보조. 아이디어 1개의 한 트랙(시장·경쟁 / 외부 API·자원 / 기술 타당성)을 웹으로 조사해 **출처 단 사실만 최종 메시지로 반환**(파일·값 안 씀). brainstorm이 트랙당 1개씩 병렬로 띄워 `research.md`로 종합.
- `plan` — decompose·plan-fe·plan-be·**distill**·arch (도메인 골격 작성 + 가지치기·정제). sketch가 있으면 plan-fe·plan-be는 sketch를 공유 소스로 **코스펙**(짝)으로 돈다.
- `sketch` — brainstorm 직후 비전 합맞춤. 설계 브리프를 클릭형 목업(`docs/brainstorming/<topic>-sketch.html`)으로 그려 사람이 "AI가 그리는 것 = 내가 그리는 것"을 눈으로 확인·구체화 → 수정을 **브리프에 되먹임**(decompose/plan이 정렬된 비전 위에서 돈다). 도메인·명세 이전이라 저충실도, 미결(`[입력 필요]`) 노출 OK.
- `dev` — 개발 리드. 개발 사항을 **티켓으로 분해**(티켓 서브에이전트)→사람 승인→**구현**(구현 서브에이전트, worktree). 단일 티켓/도메인을 받으면 리프로 그것만 발행/구현. 범위 초과면 intake로 역류.
- `intake` — 종합 창구(문서를 기획/개발로 갈라 plan·dev에 분배). 전체 구현은 별도 빌드 진입점 없이 `dev`를 직접 부른다 — dev가 HOME 참조 그래프로 BE→FE 정렬해 도메인별 구현 서브에이전트를 디스패치한다(plan이 이미 도메인 분류).
