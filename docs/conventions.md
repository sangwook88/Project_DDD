# 규약 (conventions)

FE/BE 2분할 DDD 프레임워크의 공통 규약. 스킬·에이전트가 이 문서를 공유 기준으로 삼는다.

## 분할 축 (핵심)
- **최상위 분할 = FE vs BE.** 한 도메인이 둘을 다 짊어지지 않는다(수직 도메인 금지 — 기능이 쌓이면 비대해진다).
- **FE 도메인** = 플로우(오케스트레이션) + 표현(V)만. 기능 구현 로직 금지.
- **BE 도메인** = 데이터(M) + 기능(C)만. 플로우 순서·화면·연출 금지.
- **참조는 단방향: FE → BE.** FE 요소가 BE 기능을 **링크로만** 부른다. BE는 FE를 모른다. BE 도메인 간 의존도 단방향·비순환.
- 기능 추가 = 폴더에 **파일 추가**(FE는 `요소/<노드>.md`, BE는 `기능_<name>.md`)이지 한 문서를 부풀리는 게 아니다.
- **순서는 두 방향이다.** ① **기획 순서 = FE-first** — plan-fe로 FE 플로우·요소를 먼저 구체화하고, 그 요소가 무엇을 부르는지에서 BE 도메인/기능을 *도출*한다(decompose의 BE는 잠정). ② **구현 순서 = BE-first** — FE가 부르는 기능이 먼저 있어야 하므로 dev/ticket이 HOME 참조 그래프로 BE→FE 위상 정렬. 둘을 혼동하지 않는다.

## 분할 granularity (위키-정렬 세분할)
도메인 경계 = **LLM Wiki 구조 자체**다. 기능/관심사별로 잘게 가른다 — 기획→개발이 위키 골격을 1:1로 따라가도록(`docs/HOME.md`가 곧 위키 해부도). **boundary-YAGNI로 굵게 합치지 않는다**: 의심스러우면 합치는 게 아니라 가른다.
- **분할 기준은 "책임이 다른가"가 아니라 "각자 자기 데이터/관심사를 소유하는가".** 얇아도 별개 관심사(예: HITL 검토)면 분리가 정당하다. 단 공유 필드는 **소유자 1개 + 단방향 참조**(BE 데이터 단일 소유 규칙과 일관).
- 게이트에서 **반사적 merge(하나로) 추천을 하지 않는다.** 합치는 건 두 관심사가 실제로 같은 데이터를 한 주체로 소유할 때만, 사람이 명시 결정.

## 위키 루트
- 위키 루트는 `docs/` 직접.
  - `docs/HOME.md` — 도메인 지도(FE/BE 목록 + FE→BE 참조 그래프).
  - `docs/CONTEXT.md` — 용어·공유 개념.
  - `docs/fe/<name>/` — FE 도메인 폴더.
  - `docs/be/<name>/` — BE 도메인 폴더.
  - `docs/arch/ARCHITECTURE.md` — 전역 규약 + 기술 스택(arch 산출).
  - `docs/brainstorming/` — brainstorm 설계 브리프.
  - `docs/roadmap.md` — 버전 로드맵(v1→vN 스코프 표 + **현재 타깃 버전**, roadmap 산출).

## 버전 게이트 (현재 타깃 버전)
- `roadmap`이 핵심 기능 목록을 버전(v1→vN, 가변 N)으로 자르고 `docs/roadmap.md`에 **현재 타깃 버전**을 표시한다(MVP=v1). 버전 경계·우선순위는 AI가 짓지 않고 사람이 확정한다.
- `decompose`·`plan-fe`·`plan-be`·`ticket`은 **현재 타깃 버전의 포함 기능** 범위 안에서만 돈다 — 범위 밖 기능은 다음 버전 슬롯에 둔 채 도메인으로 가르거나 명세하지 않는다. roadmap이 없으면(버전 미적용 프로젝트) 기능 전체가 범위.
- 버전을 올리려면(현재 버전 출시 후 다음 착수) `docs/roadmap.md`의 현재 타깃 버전 줄을 사람이 갱신한 뒤 decompose부터 다시 돈다.

## FE 도메인 (`docs/fe/<name>/`)
- 표준 구조: `README.md`(도메인폴더-README 템플릿) + `플로우.md`(루트 고정·단일, mermaid + FE 전체 값) + `요소/<노드>.md`(노드 1 = 파일 1, 요소 템플릿) + `일지.md`.
- 요소 §호출하는 기능 = BE 도메인 기능 **링크만**. 구현 로직 금지.
- 금지: 플로우를 단계폴더(C/·M/·V/)에 두기, 노드 상세를 `요소/` 밖에 흩뿌리기.

## BE 도메인 (`docs/be/<name>/`)
- 표준 구조(평평): `README.md` + `데이터.md`(M, 소유 테이블/enum 한 파일) + `기능_<name>.md`(C, 기능당 1파일) + `일지.md`.
- 공유 데이터는 `데이터.md`에 한 번만, 기능은 링크 참조. 기능 문서는 "무슨 데이터를 읽고 어떻게 처리하나"만(언제 부르나는 FE가 정함).

## 값 생성 금지
- AI는 수치·수량·비율·규칙·계산식·enum 값 의미를 **짓지 않는다**.
- 빠진 값은 `*[입력 필요: …]*` 슬롯으로 비운다. AI가 짓는 건 ① 뼈대 문장 ② 슬롯 ③ 질문.
- 빈 슬롯이 남은 도메인은 dev 오케스트레이션/implement.ps1에서 막고(기획 트랙=plan으로) 사람에게 돌린다.

## 일지 하네스 (쓰기 전용)
- `일지.md`는 **쓰기만 하고 읽지 않는다** — 디버깅용 결정 로그다. 쌓인 이력을 매번 읽으면 토큰만 늘고 환각을 부른다(필요할 때 사람이 본다).
- 의미 있는 변경(데이터 구조·규칙·스키마·enum·관계·플로우·시점 등 "이렇게 하기로 했다") 후 `일지.md`에 항목 1개 추가 + `현재 상태 요약` 갱신.
- 오타·링크 정리 같은 무가치 변경은 제외.

## 패턴 정책 (TS/DM)
- **BE 도메인**에만 적용(기능 C의 로직 패턴). FE는 플로우+V라 해당 없음.
- 도메인별 기본값을 `docs/arch/ARCHITECTURE.md` §패턴 정책에서 정한다 — **기획 QA 후 `arch` 단계**에서 기술 스택과 함께 결정.
  - **TS(트랜잭션 스크립트)** — 단순 CRUD·절차적, 규칙이 얇을 때.
  - **DM(도메인 모델)** — 규칙·불변식·상태가 풍부할 때.
- BE 도메인 `README.md`에 채택값 + 근거. 기본값과 어긋나면 갈림길로 올려 묻는다.

## 명명·언어
- 코드·식별자: 영문. 주석·문서: 한국어. 도메인 slug 영문(`fe/`/`be/` 트랙), 요소·기능 파일명 한국어 허용.
- 명명·직렬화 컨벤션은 ARCHITECTURE를 따른다.

## 구현 경계
- 구현 에이전트(`dev`)는 **개발 리드**다 — 개발 사항을 받으면 티켓으로 분해해 **티켓 서브에이전트**로 발행하고, 사람 승인 후 worktree에서 **구현 서브에이전트**로 구현시킨다(intake/직접 호출 경로). 단일 도메인·티켓을 배정받으면 **리프**로 그것만 계약서대로 구현한다(서브에이전트로 불릴 때). 도메인 여럿/지도 전체 구현도 별도 빌드 진입점 없이 dev가 HOME 참조 그래프로 BE→FE 정렬해 디스패치한다. 계약이 FE/BE를 선언하므로 트랙별 에이전트를 가르지 않는다(구현 에이전트는 한 종류).
- 경계 밖 파일 수정·재설계·리네이밍·겸사겸사 리팩터·새 의존 추가 금지. 참조 도메인(FE→BE, BE→BE)은 읽기만.
- 모호하거나 빈 슬롯이면 멈추고 보고. push는 사람이.

## 변경 접수 (raw → intake)
- 운영 중 들어오는 회의록·신규 기획·리팩토링 문서는 `raw/*.md` 인박스에 떨군다. `intake` 스킬이 스캔하고, 문서 1개당 git 브랜치(worktree)에서 `intake` 에이전트를 1개씩 돌린다.
- `intake` 에이전트(종합 창구)는 문서를 **부분별로** 가른다: **새 도메인 경계** 필요 → 멈추고 사람에게 `decompose` 반환(경계는 사람 게이트, AI가 경계를 짓지 않는다). **기획 부분** → `plan`이 문서 수정(+FE 플로우가 바뀌면 `qa`가 HTML 재생성); 개발이 유발되면 plan이 "개발 인계 메모"를 올려 dev로 넘긴다. **개발 부분** → `dev`가 티켓으로 분해·발행하고 멈춤(사람이 티켓 검수) → 재트리거 시 `dev`가 구현(2단계 정지). 한 문서가 기획·개발을 둘 다 담으면 plan 먼저 → dev. 계약·경계를 넘는 일을 발견하면 dev는 짓지 말고 intake로 역류시킨다.
- 모든 intake 작업은 배정 브랜치에 **로컬 커밋만** — push·merge·PR은 사람. 처리된 문서는 `raw/_done/`로 옮겨 중복 접수를 막는다.

## 단계별 에이전트 분담
- 기획 전단 단계는 메인 스레드 스킬로 직접 부르거나 서브에이전트로 돌릴 수 있다. brainstorm(아이디어 다듬기)·roadmap(버전 스코프 자르기)은 사람과 대화로 확정하는 단계로 남고(brainstorm은 거시 목표 구체화 전에 리서치 서브에이전트 3트랙을 병렬로 돌려 시장·API·타당성을 모은다), 나머지는 전부 에이전트 처리된다.
- `research` — brainstorm 보조. 아이디어 1개의 한 트랙(시장·경쟁 / 외부 API·자원 / 기술 타당성)을 웹으로 조사해 **출처 단 사실만 최종 메시지로 반환**(파일·값 안 씀). brainstorm이 트랙당 1개씩 병렬로 띄워 `research.md`로 종합.
- `plan` — decompose·plan-fe·plan-be·**distill**·arch (도메인 골격 작성 + 가지치기·정제).
- `qa` — 기획 QA. FE 도메인 HTML(`_qa/<fe>.html`) + 7렌즈 누락 초안 **생성** → 사람 클릭·피드백 → 확정 누락을 문서에 **in-place 융합**(2단계). 직접 플레이하지 않고 HTML만 만든다.
- `dev` — 개발 리드. 개발 사항을 **티켓으로 분해**(티켓 서브에이전트)→사람 승인→**구현**(구현 서브에이전트, worktree). 단일 티켓/도메인을 받으면 리프로 그것만 발행/구현. 범위 초과면 intake로 역류.
- `intake` — 종합 창구(문서를 기획/개발로 갈라 plan·dev에 분배). 전체 구현은 별도 빌드 진입점 없이 `dev`를 직접 부른다 — dev가 HOME 참조 그래프로 BE→FE 정렬해 도메인별 구현 서브에이전트를 디스패치한다(plan이 이미 도메인 분류).
