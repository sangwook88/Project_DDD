# 도메인 수직 워크플로우 재편 — 설계

Project_DDD를 **기능별 수직 도메인** 중심의 4단계 흐름으로 재편한다. 기존 씬/데이터 2분할 파이프라인(plan-*)을 내리고, 검증된 원칙만 새 척추에 흡수한다.

## 목표

아이디어를 받아 → 도메인으로 나눠 사람이 확정 → 도메인별 역할·구현목표를 한 페이지 계약서로 **전부** 명세 → 도메인별 서브에이전트로 병렬 구현 → 이후 이해·수정은 도메인 페이지(LLM 위키) 하나로.

## 핵심 결정 (확정됨)

- **도메인 축** = 기능별 수직 도메인. 각 도메인이 프론트+백을 세로로 관통. AI 제안 → 사람 확정.
- **명세 시점** = 모든 도메인을 구현 전에 다 명세("다 만들어두고").
- **위키 단위** = 도메인당 1페이지. 그 페이지가 곧 계약서이자 살아있는 위키.
- **위키 루트** = `docs/` 직접 (별도 하위 폴더 없음).
- **구현 백엔드** = 세션 내 Agent 병렬 / `implement.ps1`(브랜치+codex/claude) 둘 다 지원. **ddd-build가 서브에이전트 띄우기 직전에 사람에게 선호 방식을 물어** 그대로 진행.
- **기존 plan-* 계열** = 전부 아카이브. 7렌즈 HTML 시뮬은 선택적 부가기능으로 강등.
- **재편 방식** = 하이브리드(C): 새 4단계 척추 + 검증된 원칙(`[입력 필요]` 슬롯 / 일지 / TS·DM 패턴 정책)만 흡수.

## 전체 흐름

```
① 분할 확정      ② 도메인별 명세(전부)   ③ 도메인별 구현            ④ 위키 유지
ddd-decompose →  ddd-spec            →  ddd-build              →  (도메인 페이지)
HOME 도메인지도   docs/domains/<n>.md     Agent 병렬 | implement.ps1   이해·수정의 단일 소스
```

## 컴포넌트

### Phase 1 — `ddd-decompose` (skill, 신규)
- **입력**: 브레인스토밍 산출 / 아이디어 / 기존 위키.
- **동작**: 기능을 수직 도메인으로 가르는 초안을 제안하고 **한 번에 하나씩** 사람이 확정. 기존 도메인과 중복·의존을 짚는다.
- **산출**: `docs/HOME.md` — 도메인 목록 + 한 줄 역할 + 의존 간선(그래프).
- **원칙**: 값 생성 금지, 한 번에 한 갈림길.

### Phase 2 — `ddd-spec` (skill, 신규)
- **동작**: 확정된 **모든** 도메인에 대해 도메인당 1페이지 계약서를 작성. 구현은 시작하지 않는다.
- **산출**: `docs/domains/<name>.md` (템플릿 `templates/도메인.md`).
- **페이지 고정 절**:
  - `역할` — 이 도메인이 무엇을 책임지는가.
  - `구현목표 / 수용기준` — 완료 판정 기준.
  - `경계 (하지 말 것)` — 범위 밖.
  - `의존` — 다른 도메인 (읽기/호출/구독).
  - `패턴` — TS(트랜잭션 스크립트) / DM(도메인 모델) 택1 + 근거.
  - `상태` — not-started / in-progress / done.
  - `일지` — 결정 이력 누적.
- **선택 절**: `씬(플로우·V)`, `데이터(M·C)` — 프론트/백 디테일이 있는 도메인만.
- **흡수 원칙**: AI는 값을 짓지 않고 `[입력 필요: …]` 슬롯으로 비움. 의미 있는 변경 시 일지 1줄.

### Phase 3 — `ddd-build` (skill+agent, 신규)
- **입력**: `docs/HOME.md`(의존 그래프) + 도메인 페이지들.
- **동작**:
  1. 의존 그래프로 **독립 도메인을 wave로 묶어** 실행 순서를 정한다.
  2. **서브에이전트 띄우기 직전, 사람에게 백엔드 선호를 묻는다** — `세션 내 Agent 병렬` vs `implement.ps1`.
  3. 선택대로 각 도메인을 구현. 서브에이전트는 자기 도메인 페이지를 계약서로, `docs/arch/ARCHITECTURE.md`를 규약으로 읽고 **구현만** 한다(범위 경계 엄수, 모호하면 멈추고 보고).
  4. 도메인 완료 시 페이지 `상태` + `일지` 갱신.
- **서브에이전트 정의**: `agents/ddd-domain-impl.md` (콜드 스타트로 도메인 1개 구현).
- **백엔드 A (Agent 병렬)**: Claude가 한 세션에서 Agent 툴로 독립 도메인들을 동시 구현.
- **백엔드 B (`implement.ps1`)**: 도메인당 브랜치 따고 codex/claude 헤드리스. 도메인 페이지를 티켓처럼 입력.

### Phase 4 — 위키 유지
- 별도 스킬 없음. **도메인 페이지가 살아있는 위키**. 이후 이해·수정은 이 페이지를 통해. `HOME`이 색인, `일지`가 결정 이력.

## 기존 자산 처리

| 자산 | 처리 |
|---|---|
| `dev-arch` | **유지(슬림)** — 전역 규약(레이어·의존·명명) + TS/DM 정책 표만. |
| `implement.ps1` | **유지** — 선택 백엔드. 입력을 티켓 → 도메인 페이지로 확장. |
| `dev-ticket` | **흡수** — 도메인 페이지가 계약서 역할을 하므로 별도 티켓 단계 폐지(아카이브). |
| `plan-advise/document/scene/data/distill` | **아카이브** |
| `plan-qa` + `plan-simulate` | **아카이브** — 7렌즈 시뮬은 선택적 부가기능으로 강등. |
| `templates/기능·데이터·요소·플로우` | **아카이브** — `templates/도메인.md`로 대체. |
| `templates/ticket.md`, `sim.html` | ticket은 implement.ps1 백엔드용 보존, sim은 부가기능으로 보존. |

아카이브 위치: `archive/`로 이동(이력 보존). README 파이프라인 표 새 4단계로 교체.

## 파일 배치 (재편 후)

```
skills/
  ddd-decompose/SKILL.md
  ddd-spec/SKILL.md
  ddd-build/SKILL.md
  dev-arch/SKILL.md            (슬림)
agents/
  ddd-domain-impl.md
scripts/
  implement.ps1                (선택 백엔드)
templates/
  도메인.md                    (신규, 주력)
  ticket.md / sim.html         (보존)
docs/
  HOME.md                      (도메인 지도)
  CONTEXT.md                   (용어/공유 개념)
  domains/<name>.md            (도메인당 1페이지 = 위키)
  arch/ARCHITECTURE.md         (전역 규약, 슬림)
archive/                       (내려진 plan-* + 구 템플릿)
```

## 의존·데이터 흐름

- `ddd-decompose` → `HOME.md`(도메인 + 의존 그래프) 생성.
- `ddd-spec` → `HOME.md` 읽고 각 `domains/<name>.md` 생성(슬롯 포함).
- 사람이 슬롯 채움.
- `ddd-build` → `HOME.md` 그래프로 wave 결정 → 백엔드 선택 질의 → 도메인 페이지를 계약서로 구현 → 상태/일지 갱신.

## 에러·경계

- AI는 수치·규칙·계산식을 짓지 않는다 → `[입력 필요]` 슬롯. 빈 슬롯이 남은 도메인은 build에서 막고 사람에게 돌린다.
- 서브에이전트는 도메인 페이지 `경계(하지 말 것)`를 절대 넘지 않는다. 모호하면 구현 말고 보고 후 정지.
- 의존 순서 위반 방지: 의존 대상이 done이 아니면 그 도메인은 다음 wave로 미룬다.

## 테스트 / 검증

- 프레임워크 자체는 문서·스킬셋이므로, 검증은 "대표 도메인 1개를 4단계로 통과"시키는 드라이런으로 한다(decompose→spec→build 한 도메인).
- 각 스킬 SKILL.md는 frontmatter(name/description) + 트리거 문구를 갖춰 호출 가능해야 한다.

## 범위 밖 (YAGNI)

- 자동 의존 그래프 시각화 UI.
- 7렌즈 시뮬 재작성(기존 보존만).
- 도메인 간 자동 머지/충돌 해소(사람이 검토·커밋).
