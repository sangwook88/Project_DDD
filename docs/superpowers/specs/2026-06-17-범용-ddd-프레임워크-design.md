# 범용 DDD 기획→구현 프레임워크 설계

- 작성일: 2026-06-17
- 상태: 설계 합의 완료 (구현 계획 작성 직전)
- 형태: 어떤 프로젝트든 `.claude/`에 드롭인하는 **마크다운 스킬·에이전트 + 폴더 규약 + 템플릿 + 구현 스크립트 1개**

## 1. 목표와 배경

DsTurn 레퍼런스(게임 기획용 `gd-*`/`dev-*` 스킬·에이전트)는 검증된 구조를 갖지만 **게임(TRPG 플레이스루·카드 판정 타임라인·Unity `Assets/기획`)에 특화**돼 범용성을 잃었다.

이 프레임워크의 목표: 그 *구조·철학*만 일반화해 **어떤 프로젝트(웹·서비스·CLI 등)든 기획 단계부터 DDD 중심으로 구현까지 끌고 가는 범용 드롭인 프레임워크**를 만든다. 게임 어휘는 전부 걷어내고 중립 어휘로 바꾼다.

핵심 방침:
- **극한의 DDD, 단 두 바운디드 컨텍스트로.** 모든 기능을 **씬(프론트: UI+플로우)**과 **데이터(백엔드: 데이터+기능)**로 가른다.
- **LLM 위키처럼 돈다.** 목차·용어집·도메인 위키·일지로 프로젝트 지식이 축적·검색된다.
- **AI는 값을 짓지 않는다.** 수치·규칙·계산식·enum 의미는 `[입력 필요]` 슬롯으로 비우고 사람에게 묻는다.
- **에이전트가 오케스트레이션, 스킬이 재사용 기능.**
- **DDD 패턴 타협.** 단순 절차 = 트랜잭션 스크립트(비즈니스 로직 패턴), 규칙·불변식 풍부 = 도메인 모델(도메인 패턴) — 도메인/기능마다 트레이드오프로 택1.
- **드롭인.** 대상 프로젝트 `.claude/`에 투입, 위키·티켓은 그 프로젝트에 생성.

## 2. 두 바운디드 컨텍스트 (DDD 분할 규칙)

| 컨텍스트 | 담당 | 성분 | 산출 위치 |
|---|---|---|---|
| **씬(Scene) 도메인** | UI 요소 + 플로우 (프론트) | 오케스트레이션 + 표현(V) | `<wiki>/scene_<name>/` |
| **데이터(Data) 도메인** | 내부 데이터 + 기능 (백엔드) | 데이터(M) + 기능(C) | `<wiki>/data_<name>/` |

- **흐름·화면·전환** → 씬. **무엇이 무슨 값을 갖고 어떻게 계산되나** → 데이터.
- 대부분의 "기능"은 둘 다 → 성분별로 쪼개 각각 라우팅한다.
- 씬 요소 문서의 §호출기능은 데이터 기능 **링크만**(구현 로직 금지). 데이터 기능 문서는 "무슨 데이터를 읽고 어떻게 처리하나"만(언제 부르나는 씬이 정함).
- 단계 표기: **M**=데이터 · **C**=기능 · **V**=표현.

## 3. 파이프라인 (기획→구현)

```
① plan-advise   막연한 아이디어 → 씬/데이터/둘다 분류 + 함의·엣지케이스 미리보기 (읽기전용)
       ↓ 핸드오프
② plan-document  자유형식 → 분류·라우팅 → plan-scene/plan-data 로 골격 끌어내기
                 (신규 vs 기존 도메인 판별) → plan-distill 로 완결 문장 다듬기  = LLM 위키 구축
       ↓
③ plan-qa        기획 단 시뮬레이션(토큰 절약형):
                 plan-simulate 가 단일 HTML 생성(예시데이터+버튼 플로우 워크)
                 → 하단에 [씬 플로우 누락] + [데이터 미고려 기능] 적재
                 → 끝나면 취합해 위키에 in-place 융합 (빈틈 제거)
       ↓
④ dev-arch       전역 아키텍처 1회: 레이어 + 패턴 정책(트랜잭션 스크립트 ↔ 도메인 모델 타협)
       ↓
⑤ dev-ticket     스펙 → 도메인별 자기완결 티켓(branch frontmatter) + 기능별 패턴 선택
       ↓
⑥ scripts/implement.ps1   티켓 → base에서 branch 따고 → codex(기본)/claude 로 "구현만"
```

각 단계는 단일 목적이고, 다음 단계를 명시하며, 사람 확정 게이트를 둔다.

## 4. 구성 요소 (프레임워크가 ship하는 것)

### 4.1 에이전트 (오케스트레이터, 대화형, `agents/`)

| 에이전트 | 책임 | DsTurn 원형 |
|---|---|---|
| `plan-advise` | 아이디어 분류(씬/데이터/둘다)·함의·엣지 미리보기. 읽기전용. → plan-document 토스 | gd-advice |
| `plan-document` | 단일 진입점: 접수·분류·라우팅, 복잡 기능 staging, scene/data/distill 위임. 신규 vs 기존 도메인 판별 | gd-document |
| `plan-qa` | 시뮬레이션 오케스트레이션: HTML 생성 지시 → 누락 취합 → 위키 in-place 융합 조율 | gd-qa |

### 4.2 스킬 (재사용 기능, `skills/`)

| 스킬 | 책임 | DsTurn 원형 |
|---|---|---|
| `plan-scene` | 씬(플로우+UI 표현) 골격 끌어내기 | gd-scene |
| `plan-data` | 데이터(데이터+기능) 골격 끌어내기 | gd-wiki |
| `plan-distill` | 완결 문장 교정, 결정이력 일지 이송 | gd-distill |
| `plan-simulate` | 단일 HTML 아티팩트 생성 + 7렌즈 누락 스캔 + in-place 융합 | gd-simulate |
| `dev-arch` | 전역 아키텍처 + 패턴 정책(TS vs DM) | dev-arch |
| `dev-ticket` | 기능 → 자기완결 티켓 + 기능별 구조/패턴 결정 | dev-ticket |

### 4.3 스크립트·문서

- `scripts/implement.ps1` — 티켓 1장을 base에서 새 branch 따고 **codex(기본) 또는 claude**로 "구현만" 시킨다(`-Engine` 플래그). 푸시 안 함.
- `templates/` — README·플로우·요소·데이터·기능·일지·티켓·시뮬HTML 정적 템플릿(토큰만 치환, 기울임 안내문 유지).
- `docs/conventions.md` — 위키 레이아웃 + 두 컨텍스트 분할 규칙 + 라우팅 + 일지 하네스 + 위키 루트 설정.
- `templates/CLAUDE.snippet.md` — 대상 프로젝트 CLAUDE.md에 붙일 도메인 일지 하네스 스니펫.
- `README.md` — 프레임워크 사용법.

## 5. 대상 프로젝트에 생기는 구조 (중립화)

```
docs/ddd/                      # 위키 루트 (conventions에서 설정 가능, 기본값; 첫 실행 시 1회 확인)
  HOME.md                      # 목차 — 씬·데이터 도메인 목록 (신규 vs 기존 판별의 출처)
  CONTEXT.md                   # 용어집 — 도메인 용어 한 줄 정의 (중복·소속 확인 출처)
  scene_<name>/                # 씬 도메인 (프론트)
    README.md · 플로우.md(mermaid+씬 값) · 요소/<노드>.md · 일지.md · [화면기획/]
  data_<name>/                 # 데이터 도메인 (백엔드)
    README.md · 데이터.md(M) · 기능_<name>.md(C) · 일지.md
  _작업중/<feature>/            # 복잡 기능 staging (경계 미분할, 분산 후 삭제)
docs/arch/ARCHITECTURE.md      # 아키텍처 + 패턴 정책
tickets/NNNN-<slug>.md         # 구현 티켓 (branch frontmatter)
_sim/<feature>.html            # 시뮬레이션 아티팩트 (임시, 융합 후 삭제)
```

- 위키 루트(`docs/ddd/`)는 conventions 기본값이며, `plan-advise`/`plan-document` 첫 실행 시 사람에게 1회 확인한다(언어·프레임워크 무관).
- 모든 도메인 폴더에 `일지.md`(결정 이력)가 있어야 한다 — 일지 하네스.

## 6. 시뮬레이션 (핵심 변경점)

기존 gd-qa의 *에이전트 직접 플레이스루*는 토큰이 과하다. 대신 **결정론적 클릭 아티팩트 + 사람 워크 + 누락 취합**으로 바꾼다.

`plan-simulate` 절차:
1. **노드별 호출 매핑** — 씬 `플로우.md`(노드/간선) + 그 씬이 부르는 `기능_*.md`를 읽어 `순서 / 노드 / 입력값 / 호출 데이터·기능 / 분기 / 출력값` 표 작성.
2. **단일 자기완결 HTML 생성** (`_sim/<scene>.html`, 의존성 0):
   - 플로우를 **순서대로** 스텝으로 렌더 — 각 노드: `진입상태(예시데이터) → 호출기능 → 출력상태`를 텍스트로.
   - 분기/선택지마다 **버튼** → 문서에 그려진 대로만 클릭 워크(없는 동작은 지어내지 않음).
   - 예시 데이터는 `[예시]`로 명시(지어낸 규칙 아님). 미정 값은 `[입력 필요]`로 그대로 노출.
   - **하단 2패널**: `씬 플로우에서 놓친 부분` / `데이터 처리에서 미고려 기능` — 7렌즈로 초안 채움, 편집 가능.
     - 7렌즈: 경계·빈값 / 분기 누락 / 입력 계약 위반 / 순서·동시성 / 상태 전이 충돌 / 실패 경로 / 루프 종료.
3. **취합·융합** — 사람이 클릭하며 누락 확정·추가 → `plan-qa`가 취합 → `plan-simulate`의 in-place 융합으로 위키 `분기·다음 전이`/`예외·실패 처리` 절에 녹임(값은 `[입력 필요]`, 문서 끝에 새 섹션 추가 금지). HTML은 임시라 융합 후 삭제(SoT = 위키), 결정이력은 일지로.

## 7. DDD 패턴 타협 (비즈니스 로직 패턴 ↔ 도메인 패턴)

- `dev-arch`의 **패턴 정책** 섹션이 도메인별 기본값을 정한다:
  - 단순 CRUD·절차적 처리 → **트랜잭션 스크립트(Transaction Script)** = 비즈니스 로직 패턴.
  - 규칙·불변식·상태가 풍부 → **도메인 모델(Domain Model)** = 도메인 패턴.
- `dev-ticket`의 **구조 결정** 섹션이 기능마다 *기존 계승 vs 더 나은 구조*를 트레이드오프로 제시해 택1한다(규약 이탈이면 일지 기록).
- 즉 "둘 중 하나를 강제"가 아니라 *기능 성격에 맞춰 타협*하도록 가이드한다.

## 8. 티켓 → 브랜치 → 구현

- `dev-ticket`이 `tickets/NNNN-<slug>.md`를 쓴다. 프런트매터: `id · title · branch(feat/<slug>) · base(기본 main) · domain · stage(M/C/V) · pattern(TS/DM) · status(draft→ready→implementing→done) · engine(codex/claude)`.
- 자기완결성 필수: 콜드 에이전트가 이 티켓만 읽고 구현 가능해야 한다(변경 파일 경로·시그니처·엣지케이스·수용 기준·범위 경계).
- `scripts/implement.ps1 -Ticket tickets/NNNN-*.md`가 `base`에서 `branch`를 따고, `engine`(codex 기본 / claude)에게 "이 티켓만 구현" 시킨다. 커밋·리뷰·푸시는 사람.

## 9. 하드 제약 (전 스킬·에이전트 공통, 신성불가침)

1. **AI는 값을 생성하지 않는다** — 수치·규칙·계산식·enum 의미는 `[입력 필요]` 슬롯. AI가 짓는 건 ① 뼈대 문장 ② 성분 슬롯 표시 ③ 빠진 슬롯 질문뿐.
2. **경계** — 씬 = 플로우+표현 / 데이터 = 데이터+기능. 섞이면 성분별 분리.
3. **일지 하네스** — 도메인 파일 편집 전 그 `일지.md`를 읽고, 의미 있는 변경 후 항목 1개 추가 + 현재 상태 요약 갱신.
4. **한 번에 한 갈림길** — 여러 도메인이 나와도 하나씩.
5. **뒤에 덧붙이기 금지** — 누락 분기는 기존 문장에 in-place 융합(문서 끝 새 섹션 금지). 결정이력은 본문 금지(일지로).

## 10. 비목표 / YAGNI

- 게임 특화 요소(TRPG 플레이스루·카드 타임라인·Unity asmdef·`Assets/` 경로) 전부 제거.
- 상주 데몬·자체 런타임·웹 UI 없음(시뮬 HTML은 1회용 정적 파일).
- 가중치 점수판 없음.
- 기존 AX 오케스트레이션 프레임워크(discover/diagnose/orchestrate)는 **완전 교체**된다.

## 11. 미정 항목

- 위키 루트 기본 경로(`docs/ddd/`)가 모든 프로젝트에 맞는지 — 첫 실행 시 사람 확인으로 보정.
- 시뮬 HTML 외 Go/Python 옵션 — 기본 HTML, 필요 시 후속 확장(이 스펙 범위 밖).
- 도그푸딩 레퍼런스 프로젝트 — 미정.
