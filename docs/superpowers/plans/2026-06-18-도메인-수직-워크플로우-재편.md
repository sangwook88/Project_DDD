# 구현 계획 — 도메인 수직 워크플로우 재편

스펙: [2026-06-18-도메인-수직-워크플로우-재편-design.md](../specs/2026-06-18-도메인-수직-워크플로우-재편-design.md)

마크다운 프레임워크 재편. 의존 순서대로(템플릿 → 규약 → 스킬 → 서브에이전트 → 오케스트레이터 → 문서 → 검증) 바텀업으로 진행한다. 각 작업은 독립 검증 가능.

규칙: 한국어 + 마크다운, 식별자 영문. 커밋은 작업 묶음 단위. push·force-push는 사람이 명시할 때만.

---

## Phase 0 — 아카이브 (기존 plan-* 내리기)

**T0.1** `archive/` 생성 후 이동(이력 보존, `git mv`):
- `skills/plan-data`, `skills/plan-distill`, `skills/plan-scene`, `skills/plan-simulate` → `archive/skills/`
- `agents/plan-advise.md`, `agents/plan-document.md`, `agents/plan-qa.md` → `archive/agents/`
- `skills/dev-ticket` → `archive/skills/` (도메인 페이지가 계약서 역할 → 폐지)
- `templates/기능.md`, `templates/데이터.md`, `templates/요소.md`, `templates/플로우.md` → `archive/templates/`
- 보존(이동 안 함): `templates/ticket.md`, `templates/sim.html`, `templates/일지.md`, `templates/CLAUDE.snippet.md`, `scripts/implement.ps1`, `skills/dev-arch`.

**검증**: `git status`로 이동 확인. `find skills agents` 에 plan-* 없음. `find archive` 에 8개 묶음 존재.

## Phase 1 — `templates/도메인.md` (주력 템플릿)

스펙 "Phase 2 페이지 고정 절"을 그대로 골격화. 모든 후속 스킬이 참조하는 토대라 먼저 만든다.

**T1.1** `templates/도메인.md` 작성:
- 프런트매터: `domain`(영문 slug), `status`(not-started|in-progress|done), `pattern`(TS|DM), `depends`(다른 도메인 slug 목록), 그리고 implement.ps1 백엔드용 `branch`/`base`/`engine`(선택, 비워둠 가능).
- 고정 절: `## 역할`, `## 구현목표 / 수용기준`, `## 경계 (하지 말 것)`, `## 의존`, `## 패턴 (TS/DM + 근거)`, `## 상태`, `## 일지`.
- 선택 절(주석으로 안내): `## 씬 (플로우·V)`, `## 데이터 (M·C)`.
- 모든 값 자리는 `*[입력 필요: …]*` 슬롯.

**검증**: 프런트매터 YAML 파싱 OK. 7개 고정 절 헤딩 존재. 슬롯 표기 일관.

## Phase 2 — `dev-arch` 슬림화

전역 규약만 남기고 씬/데이터 2분할 전제를 수직 도메인 어휘로 갱신.

**T2.1** `skills/dev-arch/SKILL.md` 편집:
- 고정 목차에서 "씬(VC)↔데이터(MC)" 최상위 매핑 → "수직 도메인 + 도메인 내 레이어"로 표현 조정.
- `§3 패턴 정책(TS/DM)`은 유지하되, 도메인 분류 표가 `docs/HOME.md` 도메인 목록을 참조하도록.
- "시작 전 읽기"에서 `<wiki>` 경로를 `docs/` 직접으로.
- 산출물 경로 `docs/arch/ARCHITECTURE.md` 유지.
- description/트리거 문구 갱신.

**검증**: frontmatter name=dev-arch 유지. plan-* 깨진 링크 없음(`grep -r plan- skills/dev-arch`). 패턴 정책 절 존재.

## Phase 3 — `skills/ddd-decompose/SKILL.md` (Phase 1: 분할 확정)

**T3.1** 신규 스킬 작성:
- frontmatter: `name: ddd-decompose`, description + 트리거("도메인 나누자", "분할 확정", "ddd-decompose").
- 동작: 입력(브레인스토밍/아이디어/기존 위키) → 기능별 수직 도메인 초안 제안 → **한 번에 하나씩** 확정 → 기존 도메인 중복·의존 점검.
- 산출: `docs/HOME.md` — 도메인 목록 + 한 줄 역할 + 의존 간선. (HOME 없으면 생성, 있으면 갱신.)
- 흡수 원칙 명시: 값 생성 금지, 한 번에 한 갈림길.
- 종료: "다음 = ddd-spec" 안내 + 링크.

**검증**: frontmatter 파싱 OK. HOME.md 산출 형식(도메인/역할/의존) 본문에 명시. 다음 단계 링크가 `ddd-spec`을 가리킴.

## Phase 4 — `skills/ddd-spec/SKILL.md` (Phase 2: 도메인별 명세)

**T4.1** 신규 스킬 작성:
- frontmatter: `name: ddd-spec`, description + 트리거("도메인 명세", "스펙 채우자", "ddd-spec").
- 전제: `docs/HOME.md` 존재.
- 동작: HOME의 **모든** 도메인에 대해 `templates/도메인.md` 복제 → `docs/domains/<name>.md` 생성. 한 페이지씩 순차. 값은 슬롯으로 비움.
- 패턴(TS/DM)은 dev-arch 정책 기본값에서 출발, 어긋나면 갈림길로.
- 의미 있는 변경 시 일지 1줄.
- 종료: 빈 슬롯 채우기 안내 + "다음 = ddd-build".

**검증**: 전제(HOME.md)·산출(`docs/domains/<name>.md`)·템플릿 참조 경로가 본문에 정확. 다음 단계 링크 `ddd-build`.

## Phase 5 — `agents/ddd-domain-impl.md` (서브에이전트 정의)

**T5.1** 신규 에이전트 작성:
- frontmatter: `name: ddd-domain-impl`, description(콜드 스타트로 도메인 1개 구현), `tools`(Read/Glob/Grep/Edit/Write/Bash), `model: opus`.
- 입력 계약: 도메인 페이지 경로 1개 + `docs/arch/ARCHITECTURE.md`.
- 규칙(implement.ps1 프롬프트와 동형): 페이지의 `구현목표/수용기준`대로만, `경계(하지 말 것)` 엄수, 모호하면 멈추고 보고, 코드 영문/주석 한국어, 완료 시 변경 요약 + 일지 1줄, push 금지.

**검증**: frontmatter(name/tools/model) 유효. "경계 엄수 / 모호 시 정지" 규칙 명시.

## Phase 6 — `implement.ps1` 백엔드 확장 (도메인 페이지 입력)

**T6.1** `scripts/implement.ps1` 확장:
- `-Ticket` 외 `-Domain <docs/domains/x.md>` 입력 수용(또는 `-Ticket`이 도메인 페이지도 받게 일반화). 프런트매터 `branch`/`base`/`engine` 동일 규약 재사용.
- 프롬프트의 "읽을 티켓" → "읽을 도메인 페이지"로, 규약 SoT는 ARCHITECTURE 유지.
- 기존 ticket 입력 하위호환 보존.

**검증**: `pwsh scripts/implement.ps1 -Domain docs/domains/<샘플>.md -DryRun` 가 브랜치 계획 + 프롬프트를 출력(엔진 미실행). 기존 `-Ticket ... -DryRun` 도 여전히 동작.

## Phase 7 — `skills/ddd-build/SKILL.md` (Phase 3: 오케스트레이션)

**T7.1** 신규 스킬 작성:
- frontmatter: `name: ddd-build`, description + 트리거("도메인 구현하자", "빌드", "ddd-build").
- 전제: `docs/domains/*.md` 명세 완료(빈 슬롯 남은 도메인은 막고 사람에게 돌림).
- 동작:
  1. `docs/HOME.md` 의존 그래프로 독립 도메인을 **wave**로 묶음.
  2. **서브에이전트 띄우기 직전, 사람에게 백엔드 선호 질의** — `A) 세션 내 Agent 병렬` vs `B) implement.ps1`.
  3. A 선택 → wave 내 도메인마다 `Agent(subagent_type: ddd-domain-impl)` 병렬 디스패치, 도메인 페이지를 계약서로.
     B 선택 → wave 내 도메인마다 `pwsh scripts/implement.ps1 -Domain docs/domains/<n>.md` 안내(사람 검토·커밋).
  4. 도메인 완료 → 페이지 `상태: done` + 일지 갱신. 의존 충족 후 다음 wave.
- 종료: 완료/미완 도메인 요약.

**검증**: 백엔드 선택 질의가 "서브에이전트 띄우기 직전"으로 본문에 명시. wave/의존 처리 규칙 존재. 빈 슬롯 차단 규칙 존재. ddd-domain-impl·implement.ps1 링크 정확.

## Phase 8 — README · 규약 · 위키 토대

**T8.1** `README.md` 파이프라인 표를 새 4단계로 교체(분할→명세→구현→위키), 두 컨텍스트 설명을 "수직 도메인 + 도메인 내 씬/데이터 레이어"로 갱신, 아카이브 안내.

**T8.2** `docs/conventions.md` 재작성(삭제 상태였음): 위키 루트 `docs/`, 도메인 페이지 규약, 슬롯·일지·TS/DM 원칙, 영문 식별자.

**T8.3** (선택) `docs/HOME.md`·`docs/CONTEXT.md`는 런타임 산출물이므로 빈 골격만 두거나 생략 — ddd-decompose가 생성. 결정: 빈 골격 두지 않음(스킬이 생성).

**검증**: README에 plan-* 잔존 링크 없음(`grep -rn plan- README.md`). conventions.md 존재 + 위키 루트 `docs/` 명시.

## Phase 9 — 드라이런 검증 (대표 도메인 1개)

**T9.1** 가상 도메인 1개로 4단계 통과 점검(문서만, 코드 생성 없이):
- decompose가 HOME에 도메인 1개 + 의존 기록할 수 있는지(스킬 절차 따라 수동 트레이스).
- spec이 `templates/도메인.md`로 `docs/domains/sample.md` 생성 가능한지.
- build의 백엔드 선택·wave 로직이 그 페이지를 계약서로 넘길 수 있는지.
- implement.ps1 `-Domain ... -DryRun` 실제 실행으로 프롬프트 확인.

**검증**: 4단계가 끊김 없이 이어짐(각 스킬의 "다음 =" 링크가 실제 파일 가리킴). 깨진 상호링크 0 (`grep -rn "](.*\.md)" skills agents | 링크 대상 존재 확인`).
