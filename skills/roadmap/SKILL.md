# roadmap — 버전 로드맵·스코프 관리 (기획 전단 2단계)

핵심 기능 목록을 받아 *PM처럼* 버전(v1→vN)으로 **스코프를 자른다**. 첫 버전이 비대해지지 않도록 MVP=v1에서 시작해 점증 분배하고, 이후 단계가 "현재 타깃 버전"이라는 경계 안에서만 돌도록 게이트를 건다. 전제: [brainstorm](../brainstorm/SKILL.md) 설계 브리프(핵심 기능 목록). 규약: [docs/conventions.md](${DDD_ROOT}/docs/conventions.md). 산출: `docs/roadmap.md`.

## 이 단계가 답하는 것
- **v1은 어디까지** — MVP가 풀어야 할 최소 가치. 무엇이 *있어야 출시*인가.
- **v2~vN은 무엇을 더** — 점증으로 쌓을 기능을 버전 슬롯에 배치.
- **지금 뺄 것 / 미룰 것** — YAGNI로 잘라낸 것과 그 행선지(버전).
- **버전 간 전제(의존)** — vN이 vN-1의 무엇에 기대는가.

도메인 경계·데이터·플로우·값은 **이 단계가 아니다** — [decompose](../decompose/SKILL.md) 이후 몫. 여기선 *기능을 버전에 배치*만 하고 멈춘다.

## 절대 규칙
1. **버전 경계·우선순위를 AI가 짓지 않는다.** "v1에 무엇을 넣고 무엇을 미룰지"는 제품 결정 — 사람이 확정한다. AI는 분배 *초안*과 트레이드오프, 슬롯, 질문만 만든다. "예를 들면 v1에 3개쯤" 같은 임의 배치 금지.
2. **프로젝트 값 생성 금지.** 수치·수량·비율·규칙은 짓지 않는다(규약 계승). 다루는 건 *기능을 어느 버전에* 둘지일 뿐, 기능 내부 값이 아니다.
3. **한 번에 한 갈림길.** 버전 경계 하나씩 제안 → 확정. 가능하면 객관식.
4. **YAGNI 가차없이.** 당장 가치를 증명 못 하는 기능은 뒤 버전으로 밀거나 "안 함"으로.
5. **버전 개수 고정 금지.** v1~v5로 못 박지 않는다 — 필요한 만큼만(가변 N). MVP=v1만 고정, 나머지는 기능이 차야 슬롯이 생긴다.
6. **읽기 전용 위키.** 브리프·HOME·CONTEXT·코드는 읽어 접지하되, 쓰는 건 `docs/roadmap.md`뿐.

## 시작 전 읽기
1. brainstorm 설계 브리프(`docs/brainstorming/*-brief.md`) — **핵심 기능 목록**이 입력. 없으면 "무엇을 만들고 싶으신가요" 또는 brainstorm 먼저 안내.
2. 리서치 노트(`docs/brainstorming/*-research.md`, 있으면) — 시장·경쟁·자원 근거로 우선순위 판단 보조.
3. `docs/roadmap.md` — 이미 있으면 *갱신*(버전 추가·재배치). 없으면 새로 만든다.
4. `docs/HOME.md`·`docs/CONTEXT.md`(있으면) — 기존 도메인·용어로 이미 출시된 범위 파악.

## 흐름
1. **기능 목록 수집** — 브리프의 핵심 기능 목록을 그대로 받는다(성분 단위). 비었으면 brainstorm으로 되돌린다.
2. **MVP 가설** — "이 제품이 가치를 증명하는 최소 묶음"을 한 줄로 잡고 사람과 확인. v1의 목표 문장이 된다.
3. **버전 분배 초안 + 확정** — 기능을 v1 / 후속 / 안 함으로 가른 초안을 보여주고 **하나씩** 확정:
   - 각 기능: 어느 버전 슬롯 · 한 줄 근거(왜 지금/왜 나중) · 의존(앞 버전의 무엇을 전제).
   - 경계가 애매하거나 "v1에 넣을지 미룰지" 갈리면 **임의로 정하지 말고** 트레이드오프(넣을 때 비용 / 뺄 때 잃는 가치)로 갈림길을 올려 묻는다.
4. **버전 간 전제 정리** — vN이 vN-1의 어떤 기능·데이터에 기대는지 단방향으로. 뒤 버전이 앞 버전을 깨는 의존이 보이면 배치 재검토.
5. **현재 타깃 버전 지정** — 지금 decompose 이하로 내려보낼 버전을 하나 고정(보통 v1). 이 마커가 하류 게이트의 기준.
6. **YAGNI 패스** — 어느 버전에도 못 들어간 기능은 "안 함(이유)"으로 명시. 나중에 떠오를 근거를 남긴다.

## 산출 — docs/roadmap.md
버전 로드맵을 갱신(없으면 생성). 버전 수는 가변 — 필요한 만큼만 섹션을 둔다:

```markdown
# 버전 로드맵

**현재 타깃 버전: v1**   <!-- decompose/plan/ticket은 이 버전의 '포함 기능'만 다룬다 -->

## 스코프 표
| 기능 | v1 | v2 | v3 | … | 비고(근거·전제) |
|---|:--:|:--:|:--:|---|---|
| <기능 A> | ✅ |  |  |  | MVP 핵심 |
| <기능 B> |  | ✅ |  |  | v1의 <A>에 의존 |
| <기능 C> |  |  |  |  | 안 함 — *[이유]* |

## v1 — <목표 한 줄>
- **목표(가치)**: 이 버전이 증명하는 것.
- **포함 기능**: <A> …
- **제외(다음으로)**: <B>(→v2) …
- **전제(의존)**: 없음(MVP) 또는 *[입력 필요]*.

## v2 — <목표 한 줄>
- **목표**: … **포함**: <B> … **전제**: v1의 <A>.

<!-- 필요한 만큼 vN 섹션 추가. 개수 고정하지 않음. -->

## 안 함 (YAGNI)
- <C> — 뺀 이유. 떠오르면 어느 버전에서 다시 볼지.
```

- 기능명·근거는 한국어, 식별자는 영문. 값(수치·규칙)은 여기서 짓지 않는다 — 기능을 *어느 버전에* 둘지만.
- **현재 타깃 버전** 줄이 하류 게이트의 단일 소스다. 버전을 올리려면(v1 출시 후 v2 착수) 이 줄을 사람이 갱신한다.

## 종료 — decompose로 핸드오프
확정한 버전 수 + 현재 타깃 버전 + 그 버전 포함 기능 목록 요약 + "다음 = [decompose](../decompose/SKILL.md)로 **현재 타깃 버전 범위만** FE/BE 도메인 분할" 안내. 아직 경계가 흐물거리면 3~4를 더 돈다. 한국어 + 마크다운, 식별자 영문.
