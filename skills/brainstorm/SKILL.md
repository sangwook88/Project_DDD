# brainstorm — 거시 목표 빚기 (기획 전단 1단계)

막연한 아이디어를 *프로젝트 값을 짓지 않고* **거시 목표**로 빚는다. 세세한 도메인 분할·명세는 안 한다 — "무엇을 / 왜 / 누구를 위해 / 핵심 기능"까지. 프레이밍 → 리서치 디스패치(서브에이전트) → 종합·구체화 → 브리프. 규약: [docs/conventions.md](${DDD_ROOT}/docs/conventions.md). 산출: `docs/brainstorming/<topic>-research.md`(리서치 노트) + `docs/brainstorming/<topic>-brief.md`(설계 브리프).

## 이 단계가 답하는 것 (거시 목표)
- **문제·가치·경험** — 어떤 문제를 풀고, 어떤 가치를 만들고, 어떤 경험을 선사하나.
- **누구를 위한 제품** — 대상 사용자.
- **핵심 기능** — 무엇이 있어야 하나(성분 단위, 값은 슬롯).

세세한 도메인 경계·데이터·플로우·엣지 해소값은 **이 단계가 아니다** — [decompose](../decompose/SKILL.md) → plan-fe/plan-be 몫. 여기선 그 디테일을 *함의*만 하고 멈춘다.

## 절대 규칙
1. **프로젝트 값 생성 금지.** 우리 제품이 정할 수치·수량·비율·방식·규칙·계산식·enum 값 의미를 짓지 않는다. "예를 들면 3쯤" 같은 예시 수치도 금지 → `[입력 필요]`. **단, 리서치가 가져온 외부 사실**(경쟁사 가격·API 한도·라이선스 등)은 **출처를 단 '참고 근거'로만** 적을 수 있다 — 외부 관측 사실 ≠ 우리가 지을 프로젝트 값. 둘을 섞지 않는다.
2. **한 번에 한 질문.** 한 메시지에 한 갈림길. 가능하면 객관식.
3. **읽기 전용 위키.** `HOME.md`·`CONTEXT.md`·코드는 읽어 접지하되, 위키 문서는 안 쓴다. 쓰는 건 리서치 노트와 브리프뿐.
4. **YAGNI 가차없이.** 불필요한 기능은 모든 안에서 쳐낸다.
5. **거시까지만.** 도메인 분할·요소/기능 명세는 decompose 이후. 여기서 세분화하지 않는다.

## 흐름
1. **맥락 탐색** — `docs/HOME.md`·`docs/CONTEXT.md`·최근 커밋·관련 코드를 가볍게 훑어 기존 도메인·용어·제약 파악. 비슷한 게 있으면 짚는다.
2. **아이디어 수집** — 막연한 의도를 그대로 받는다. 비었으면 "무엇을 만들고 싶으신가요". 경로면 읽는다.
3. **프레이밍 + 리서치 브리프 (사람과)** — 한 번에 한 질문으로 조사 방향을 사람과 잡는다. ⓐ 대상 사용자·풀려는 문제축을 좁히고, ⓑ **시장·경쟁 리서치용으로 문제 정의 · 검증할 가설 · 조사 계획(범위·우선순위)을 사람과 함께 확정**한다. **이 방향 결정은 에이전트에 맡기지 않는다** — 에이전트가 혼자 지어내면 엉뚱한 데를 판다. 깊은 명세(값) 질문은 아직 안 한다.
4. **리서치 디스패치 — `research` 에이전트 3트랙 병렬.** [research 에이전트](../../agents/research.md)(절차 SoT [skills/research/SKILL.md](../research/SKILL.md))를 트랙당 1개씩 *동시에* 띄운다(한 메시지에 Agent 호출 3개). 각 트랙에 **트랙명 + 아이디어 원문 + 프레이밍 답**을, **시장·경쟁 트랙엔 + 리서치 브리프(ⓑ의 문제 정의·가설·조사 계획)**까지 입력 계약대로 준다. 에이전트는 이 계획대로 **데이터 수집→분석→인사이트→보고(시장조사 3~6단계)**만 실행한다. 트랙:
   - **시장·경쟁** — 유사 제품/기존 솔루션, 차별점, 빈틈, 사용자가 실제로 겪는 페인.
   - **외부 API·자원** — 필요할 법한 API·라이브러리·데이터 소스·연동 후보 + 한도·비용·라이선스.
   - **기술 타당성** — 실현 가능성·제약·build vs buy 후보.
   각 에이전트는 Write 없이(읽기+웹만) **출처 단 보고를 최종 메시지로 반환**한다 — 파일은 다음 단계에서 메인 스레드가 쓴다.
5. **리서치 종합 → 노트 작성** — 세 보고를 합쳐 `docs/brainstorming/<topic>-research.md`로 쓴다(아래 산출). 모순·불확실은 그대로 표시.
6. **거시 목표 구체화** — 리서치 근거 위에서 한 번에 한 질문으로 좁힌다: 문제·가치·경험 → 대상 사용자 → 핵심 기능 → 안 할 것(scope). 답이 코드·문서로 확인되면 묻지 말고 직접 본다.
7. **접근법 2~3개 제안** — 각 트레이드오프 + 추천(추천을 먼저, 왜를 설명). 리서치에서 나온 자원·제약을 근거로 건다.
8. **설계 제시 (섹션별 승인)** — 이해됐다 싶으면 거시 설계를 섹션별로 제시하고 섹션마다 "이대로 맞나요" 확인. 다루는 것: 목적(문제·가치·경험), 대상, 핵심 기능(성분 단위·값은 슬롯), 함의되는 데이터/플로우/엣지 미리보기, 건드리는 기존 도메인·용어, 안 할 것.
9. **엣지케이스 미리보기** — 경계값(0·최대·음수·초과)·실패·빈 상태·중복·동시성을 질문으로(해소값 `[입력 필요]`).

## 산출

### 리서치 노트 — `docs/brainstorming/<topic>-research.md`
트랙별로 정리, **모든 외부 수치·사실에 출처**:
- **시장·경쟁** — 유사 제품/솔루션, 차별점·빈틈, 사용자 페인.
- **외부 API·자원** — 후보 목록 + 한도·비용·라이선스(출처 링크).
- **기술 타당성** — 실현성·제약·build vs buy.
- **시사점** — 거시 목표에 주는 함의(우리 값은 여전히 슬롯).

### 설계 브리프 — `docs/brainstorming/<topic>-brief.md`
승인된 거시 설계를 쓴다:
- **거시 목표** — 문제·가치·경험 + 대상 사용자(값은 슬롯).
- **핵심 기능 목록** — 성분 단위로(BE 측 / FE 측 미리 갈라두면 decompose가 수월). 값은 `*[입력 필요: …]*`.
- **리서치 근거 요약** — 정제한 핵심 + `…-research.md` 링크.
- **건드리는 기존 도메인·용어** + 중복·충돌 메모.
- **엣지케이스 체크리스트** — 사람이 채울 분기·예외 질문 묶음.
- **안 할 것 (YAGNI)** — 의도적으로 뺀 것.

## 종료 — roadmap으로 핸드오프
"이제 버전을 자르자"가 되면 → 리서치 노트·브리프 경로 + 핵심 기능 목록 요약을 제시하고 "다음 = [roadmap](../roadmap/SKILL.md)으로 버전 로드맵(v1→vN) 스코프 분배" 안내. 아직 흐물거리면 6~9를 더 돈다. 한국어 + 마크다운, 식별자 영문.
