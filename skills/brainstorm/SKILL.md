# brainstorm — 소크라테스식 기획 (기획 전단 1단계)

막연한 아이디어를 *값을 짓지 않고* 대화로 끌어내 **설계 브리프** 한 장으로 빚는다. 구현·도메인 분할은 안 한다 — "무엇을 / 왜 / 무엇이 필요한지"까지. 규약: [docs/conventions.md](${DDD_ROOT}/docs/conventions.md). 산출: `docs/brainstorming/YYYY-MM-DD-<topic>-brief.md`.

## 절대 규칙
1. **값 생성 금지.** 수치·수량·비율·방식·규칙·계산식·enum 값 의미를 짓지 않는다. "예를 들면 3쯤" 같은 예시 수치도 금지. "무엇이 필요한지" + `[입력 필요]`까지만.
2. **한 번에 한 질문.** 한 메시지에 한 갈림길. 가능하면 객관식(아니면 열린 질문도 OK).
3. **읽기 전용 위키.** `HOME.md`·`CONTEXT.md`·코드는 읽어 접지하되, 위키 문서는 안 쓴다. 쓰는 건 브리프뿐.
4. **YAGNI 가차없이.** 불필요한 기능은 모든 안에서 쳐낸다.

## 흐름
1. **맥락 탐색** — `docs/HOME.md`·`docs/CONTEXT.md`·최근 커밋·관련 코드를 가볍게 훑어 기존 도메인·용어·제약 파악. 비슷한 게 있으면 짚는다.
2. **아이디어 수집** — 막연한 의도를 그대로 받는다. 비었으면 "무엇을 만들고 싶으신가요". 경로면 읽는다.
3. **한 번에 한 질문으로 좁히기** — 목적 · 제약 · 성공기준 · 사용자 · 안 할 것(scope). 답이 코드·문서로 확인되면 묻지 말고 직접 본다.
4. **접근법 2~3개 제안** — 각 트레이드오프 + 추천(추천을 먼저, 왜를 설명).
5. **설계 제시 (섹션별 승인)** — 이해됐다 싶으면 설계를 섹션별로 제시하고 섹션마다 "이대로 맞나요" 확인. 다루는 것: 목적, 핵심 기능(필요 성분, 값은 슬롯), 함의되는 데이터/플로우/엣지케이스 미리보기, 건드리는 기존 도메인·용어, 안 할 것.
6. **엣지케이스 미리보기** — 경계값(0·최대·음수·초과)·실패·빈 상태·중복·동시성을 질문으로(해소값 `[입력 필요]`).

## 산출 — 설계 브리프
승인된 설계를 `docs/brainstorming/YYYY-MM-DD-<topic>-brief.md`로 쓴다:
- **목적·성공기준** — 끝나면 무엇이 되나(값은 슬롯).
- **핵심 기능 목록** — 필요 성분 단위로(BE 측 / FE 측 미리 갈라두면 decompose가 수월). 값은 `*[입력 필요: …]*`.
- **건드리는 기존 도메인·용어** + 중복·충돌 메모.
- **엣지케이스 체크리스트** — 사람이 채울 분기·예외 질문 묶음.
- **안 할 것 (YAGNI)** — 의도적으로 뺀 것.

## 종료 — decompose로 핸드오프
"이제 도메인으로 가르자"가 되면 → 브리프 경로 + 요약을 제시하고 "다음 = [decompose](../decompose/SKILL.md)로 FE/BE 도메인 분할" 안내. 아직 흐물거리면 3~6을 더 돈다. 한국어 + 마크다운, 식별자 영문.
