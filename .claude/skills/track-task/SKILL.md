# Track Task — 칸반 카드 중앙 처리기 (안내데스크)

Notion 칸반 카드 1장을 **선택 → 분류 → 진행 중 이동 → 알맞은 진입점으로 라우팅 → (작업 종료·사용자 OK 시) 카드 완료** 순서로 처리한다.
카드는 기획~개발에 걸친 **정해진 태스크**이거나 **버그**다 — track-task는 그걸 갈라 이 프로젝트의 기존 파이프라인으로 **인계**한다.

**[desk](../../../skills/desk/SKILL.md)·[intake](../../../skills/intake/SKILL.md)처럼 안내데스크다 — 구현·기획·이슈해결을 직접 하지 않는다.**
분류·판정·인계와 **카드 상태(진행 중/완료) 관리**만 하고, 실제 작업은 라우팅한 스킬이 한다.
칸반은 Notion([`tools/notion/notion.py`](../../../tools/notion/notion.py)). 규약 SoT: [docs/conventions.md](../../../docs/conventions.md) · `docs/arch/ARCHITECTURE.md` · `docs/HOME.md`.

**이 스킬을 수행하는 동안 사용자에게 보내는 모든 응답·확인 질문·보고는 한글로 작성한다.**

## 절대 규칙
1. **직접 일하지 않는다.** 구현·기획·티켓·이슈해결은 라우팅한 스킬로. track-task는 분류·인계·카드 상태만.
2. **값·분류 임의 생성 금지.** 성격이 애매하면 **한 번에 한 질문**으로 확인(desk 규칙 계승).
3. **push·merge 안 함.** 브랜치·PR·머지는 라우팅된 경로(track-issue/구현 엔진)가. track-task는 카드만 만진다.
4. **완료는 사용자 게이트.** 라우팅한 작업이 실제로 끝나고 사용자가 "해결했다"고 해야 카드를 완료로.

## 0. 전제 확인
- **Notion**: 실행 위치 `tools/notion/`. `.env`(notion.py 옆)에 `NOTION_TOKEN` + `NOTION_KANBAN_DB_ID` 필요.
  없으면 `python notion.py kanban-info --url "<칸반 URL>"` 로 채우도록 안내하고 멈춘다(임의 생성 금지).
  상태 컬럼명(시작 전/진행 중/완료)이 다르면 `kanban-info` 출력의 실제 옵션명을 쓴다.
- **파이프라인**: 라우팅 대상 스킬(desk·decompose·dev·ticket·new-issue·track-issue)이 이 저장소에 있어야 한다.

## 1. 카드 선택
- **인자로 제목/일부/`page_id` 가 주어지면** 그 카드를 다룬다.
- **없으면** `python notion.py list-cards --status "시작 전"`(필요하면 `--status "진행 중"` 도)로 목록을
  보여주고 어느 카드를 처리할지 고르게 한다. 목록은 `[상태] 제목 / url / page_id` 형식이다.
- 고른 카드의 본문(할 일·세부·도메인·트랙)을 읽어 무엇을 하려는 건지 파악한다.

## 2. 분류 — 어디로 보낼지 (핵심)
카드 성격을 판정해 진입점을 정한다. 판정은 **트랙·본문 + 프로젝트 상태(docs/HOME.md 도메인·tickets/)** 로.

| 카드 성격 | 판정 기준 | 진입점(라우팅) |
|---|---|---|
| **버그** | 트랙=버그 / 기존 동작이 틀림("안 됨·오류·깨짐") | **issue 경로** → [new-issue](../new-issue/SKILL.md)로 이슈 발행 → [track-issue](../track-issue/SKILL.md)로 처리(dev단 시작: 티켓화→구현→PR·`Closes #N` 자동종료). track-issue가 범위 넓으면 decompose/dev로 쪼갠다. |
| **정해진 태스크 · 범위 넓음** | 여러 도메인·새 경계 필요·기능 묶음 | **먼저 쪼갬** → [decompose](../../../skills/decompose/SKILL.md)(새 도메인 경계·HOME 갱신) 또는 [dev](../../../skills/dev/SKILL.md)가 하위로 분해 → **하위 각각을 다시 이 표로**. |
| **정해진 태스크 · 기획** | 새 기능·미확정 스펙·플로우/화면 | **desk 경로** → [desk](../../../skills/desk/SKILL.md)가 단계 판정 → brainstorm/sketch/roadmap/decompose/plan-fe·plan-be/distill/arch/ticket 중 알맞은 단계로. |
| **정해진 태스크 · 개발** | 설계 확정된 구현거리 | **개발 경로** → 도메인 폴더(`docs/be/*`·`docs/fe/*`)가 있으면 [dev](../../../skills/dev/SKILL.md)로 바로 구현, 없으면 [ticket](../../../skills/ticket/SKILL.md)으로 티켓화 후 dev. |

- **범위 판정**: 한 도메인·한 티켓으로 닫히면 "좁음"(개발/버그 경로 바로), 여러 도메인이나 새 경계가 필요하면 "넓음"(decompose/dev 선쪼갬).
- **기획 vs 개발**: 스펙·플로우·화면이 미확정이면 기획(desk), 설계가 확정돼 구현만 남았으면 개발.
- 어디 속하는지 애매하면 후보를 객관식으로 **한 번에 한 질문**. 임의로 확정하지 않는다.

## 3. 진행 중 이동 + 라우팅
1. **카드를 진행 중으로**: `python notion.py move-card <page_id> "진행 중"`. (되돌리기 쉬운 상태변경이라 바로.)
2. **진입점 안내 + 인계** — desk 형식으로 한 줄: "이 카드는 **<성격>** 입니다 → `<진입점>` 로 진행합니다."
   그 스킬에 **카드 URL·본문을 입력으로 넘긴다** — 다운스트림 산출물(이슈/티켓/PR 본문)에 카드 URL을 박아 추적을 잇는다.
3. **범위가 넓으면** decompose/dev로 먼저 쪼갠 뒤, 나온 하위(도메인/티켓/이슈)를 각각 2단계 분류로 다시 태운다.

track-task는 여기서 인계로 끝난다 — 이슈 발행·티켓 작성·구현·기획 단계는 그 스킬이 사람 게이트를 거쳐 수행한다.

## 4. 완료 게이트 (재진입)
라우팅한 작업이 실제로 끝나고(이슈 close / PR 머지 / 티켓 구현 완료) **사용자가 "해결했다"(또는 동등한 확인)라고 하면**:
- `python notion.py move-card <page_id> "완료"`. 실패하면 로그를 보이고 알린다(자동 성공 처리 금지).
- **보고**: 어떤 경로로 처리됐는지(이슈/PR/티켓 링크) + 완료로 옮긴 카드 URL.
- 하위로 쪼갠 카드면 **하위가 전부 끝나야** 완료로 옮긴다.

track-task 자신은 push/merge/구현을 하지 않는다 — 카드 상태만 최종화한다.

## 하지 않는 것
- 직접 구현·기획·이슈해결 — 라우팅만(안내데스크).
- 분류·값 임의 생성 — 애매하면 한 번에 한 질문.
- 사용자 확인 전 카드 완료 이동 / push·merge.
- 상태 컬럼명 추측 — `kanban-info` 로 실제 옵션명 확인.
