# New Issue

GitHub **버그 리포트** 이슈를 **분석 → 예시 제시 → 확인 → 발행** 순서로 만든다.
플랫폼은 GitHub, 도구는 `gh` CLI다. 본문은 항상 3장의 버그 리포트 목차를 따른다.
**확인을 받기 전에는 절대 이슈를 발행하지 않는다.**

**이 스킬을 수행하는 동안 사용자에게 보내는 모든 응답·확인 질문·보고는 한글로 작성한다.** (이슈 제목·본문도 한글)

## 0. 전제 확인

- `gh` 가 설치/인증돼 있어야 한다. 없으면 발행 단계에서 막히니, 발행 직전 `gh auth status` 로 확인한다.
  미설치/미인증이면 사용자에게 알리고 멈춘다 (`https://cli.github.com`, `gh auth login`).
  - `gh` 가 PATH에 없는 환경이면(예: Windows 기본 설치 위치 `C:\Program Files\GitHub CLI\gh.exe`) 그 실제 경로를 호출 연산자로 풀어 쓴다: `& "<gh 경로>" <args>`.

## 1. 무엇을 이슈로 낼지 정한다

- **인자가 있으면** 그 내용을 이슈의 주제로 삼는다.
- **인자가 없으면** 현재 대화를 분석해, 어떤 프로젝트에서 어떤 문제·작업이 나왔는지 뽑는다.
  여러 개면 후보를 나열하고 무엇을 이슈로 낼지(또는 여러 개로 나눌지) 짧게 확인한다.

## 2. 대상 레포 판별

1. 기본은 현재 작업 디렉터리의 git remote: `gh repo view --json nameWithOwner -q .nameWithOwner` (또는 `git remote get-url origin`).
2. 대화가 다른 프로젝트에 관한 것이면 그 레포를 우선한다. 어느 레포인지 불명확하면 사용자에게 묻는다.

## 3. 예시 제시 (게이트)

발행 전에 아래를 그대로 보여주고 확인을 받는다:

- **레포**: `owner/repo`
- **제목**: 한 줄, 명확하게
- **본문**: 아래 **버그 리포트 목차**를 그대로 따른다.
- **라벨·담당자·마일스톤** (해당되면): 실제 존재하는 라벨만. 확신 없으면 `gh label list` 로 확인하거나 비워둔다.

### 본문 목차 (버그 리포트)

본문은 항상 다음 섹션 순서로 작성한다. 해당 정보가 없으면 빈 칸으로 두지 말고 `(미상)` 또는 확인 요청을 남긴다.

```markdown
## 현상 (Description)
무슨 일이 일어났는지 한두 줄

## 재현 방법 (Steps to Reproduce)
1. ...
2. ...

## 기대 동작 (Expected) / 실제 동작 (Actual)
- 기대: ...
- 실제: ...

## 환경 (Environment)
OS / 브라우저 / 버전 등

## 스크린샷·로그 (Screenshots / Logs)
관련 로그·이미지·링크 (있으면)
```

그리고 실제 실행할 명령을 함께 보여준다:

```
gh issue create --repo owner/repo --title "..." --body "..." [--label ...]
```

확인 질문: **"이 내용으로 발행할까요? 고칠 부분 있으면 알려주세요."**
수정 요청이면 예시를 갱신해 다시 확인. **OK 받기 전엔 발행하지 않는다.**

## 4. 발행

확인 후에만 `gh issue create ...` 실행. 본문이 길면 임시 파일에 써서 `--body-file` 로 넘긴다.
발행되면 생성된 이슈 URL을 사용자에게 보여준다. 여러 개면 하나씩 같은 절차로 반복한다.
